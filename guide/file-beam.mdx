## Overview

The Ephemeral File Beam is Neutrino's primary transport for transferring individual files or archives directly between two machines without cloud intermediary storage.

```mermaid
graph LR
    Alice["Alice (Sender)"]
    Coord["Blind Coordinator"]
    Bob["Bob (Receiver)"]
    Staging[".nwp.part File"]
    Final["Final Target File"]

    Alice -->|1. Register Keyed Room ID| Coord
    Bob -->|2. Join Room ID| Coord
    Alice <-->|3. STUN UDP Hole Punch| Bob
    Alice -->|4. FastCDC Chunks (16 MB Window)| Bob
    Bob --> Staging
    Staging -->|5. BLAKE3 Tree-Hash Verified| Final
```

## Sending Files

To send a file, invoke `neutrino send`:

```bash
neutrino send /path/to/archive.tar.gz
```

### Bandwidth Throttling

To prevent saturating an office or residential uplink, apply a maximum transfer rate in Megabits per second:

```bash
# Limit outbound speed to 500 Mbps
neutrino send ./backup.qcow2 --max-speed 500
```

### Custom Chunk Size

While 1 MB is optimal for most networks, you can override chunk boundaries:

```bash
# Set chunk target size to 2 MB
neutrino send ./raw-footage.mov --chunk-size 2
```

### Machine-Readable JSON Receipts

For automation scripts and CI/CD pipelines, use `--json`:

```bash
neutrino send ./release-assets.zip --json
```

Outputs a structured JSON object upon completion:

```json
{
  "status": "completed",
  "session_code": "amber-lynx-4192",
  "file_name": "release-assets.zip",
  "file_size": 1048576000,
  "blake3_root": "8b51d6c8b368735237b69c...7b5f",
  "transfer_duration_secs": 1.28,
  "average_speed_mbps": 6553.6
}
```

## Receiving Files

To receive a transfer, supply the session code generated by the sender:

```bash
neutrino receive amber-lynx-4192 ~/Downloads/
```

### Non-Interactive Execution

In automated scripts or headless environments where interactive prompts cannot be answered, bypass the prompt with `-y` or `--yes`:

```bash
neutrino receive amber-lynx-4192 ~/Downloads/ --yes --json
```

## Atomic Staging & Resumption

### 1. Temporary Staging Target
Files are never written directly to the target destination path while downloading. Instead, chunks stream into a hidden staging file:

```text
~/Downloads/.release-assets.zip.amber-lynx-4192.nwp.part
```

A companion `.nwp.state` checkpoint file maintains a verified bitmask of received chunks.

### 2. BLAKE3 Verification & Atomic Commitment
Upon receiving `TRANSFER_COMPLETE`, `neutrinod` recalculates the whole-file BLAKE3 root tree-hash and compares it with the manifest. Only when the hash matches is the file atomically renamed to `~/Downloads/release-assets.zip`. If any corruption occurred, the staging file is rejected.

### 3. Mid-Stream Resumption
If a connection is abruptly severed (e.g. Wi-Fi drop or laptop lid close), simply re-run `neutrino receive` with the same session code. The peers exchange their verified chunk bitmasks and immediately resume streaming from the first missing chunk without re-transmitting already-verified blocks.
