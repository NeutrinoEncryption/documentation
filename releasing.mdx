The current release is **v0.4.0**. Client releases and relay/STUN deployment are separate operations. Maintainers need repository and deployment access; users download from the Neutrino server.

<Steps>
<Step title="Choose and verify">
Use semantic versioning and document incompatible wire changes. Run the checks from `RELEASING.md`:
```bash
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```
Contribution rules additionally require the all-features Clippy check before code review approval.
</Step>
<Step title="Bump versions together">
For example, prepare the next patch after v0.4.0:
```bash
sh scripts/bump-version.sh 0.3.2
```
The script updates workspace crates, desktop/Tauri configuration, and `Cargo.lock`. Review all changes, including website release constants and documentation. Preserve historical compatibility statements: relay rendezvous requires both peers on v0.3.0 or newer, even after a release-version bump.
</Step>
<Step title="Commit and push to main">
After review, commit the version change and push `main`:

```bash
git commit -am "chore: release v0.3.2"
git push origin main
```

When CI passes on `main` and the matching version tag does not exist, CI creates it and runs the release workflow automatically. A manually pushed `v*` tag also triggers release. The workflow rejects tags that do not match the Cargo version. Check the Actions runs before retrying or creating a tag manually.
</Step>
<Step title="Verify deployment and smoke test">
The workflow builds `neutrino` and `neutrinod` for the five [targets](/installation), generates `SHA256SUMS`, uploads to `/var/www/neutrino-dl/v0.3.2/`, refreshes both installers, then updates `latest.txt`.

Check the Actions run, reinstall on two machines, check versions, and transfer a folder. Confirm contents and verified completion on both sides. Test forced relay as well as direct connectivity when validating network changes.
</Step>
</Steps>

## Rollback

Old version directories remain available. An authorized server operator can run this on the download server:

```bash
printf '%s\n' v0.4.0 > /var/www/neutrino-dl/latest.txt
```

Existing installs do not downgrade automatically. Users rerun the installer or pin `NEUTRINO_VERSION=v0.4.0`. To republish an existing tag after workflow repairs, select **Actions → release → Run workflow** with that tag.

## Deployment access

Actions uses `DEPLOY_SSH_KEY`, `DEPLOY_HOST`, and `DEPLOY_KNOWN_HOSTS`. The upload account is restricted to `/var/www/neutrino-dl`. Keep secrets in Actions secrets and pin the SSH host key.

See the source checkout's `RELEASING.md` and `deploy/SERVER.md` for maintainer procedures. Relay changes must preserve compatibility with clients in the field; see [self-hosting](/self-hosting/relay).

## Relay continuous deployment

Client releases and relay updates are independent. In the private maintainer workflow, a push to `main` changing `bins/neutrino-relay/` builds a static binary and uploads it. CI invokes only the authorized `/usr/local/sbin/neutrino-relay-install` script through sudo. That script restarts the service and rolls back if startup fails.

Relay changes must preserve the registration envelope and pairing notice for clients already in the field. The open-source relay has its own [deployment guide](/self-hosting/relay); STUN is a separate service. Inspect the current workflow definitions before operating a release, since deployment automation can change.
