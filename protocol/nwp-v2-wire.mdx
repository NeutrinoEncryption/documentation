---
title: "NWP v2 wire framing"
description: "The implemented 24-byte header and transfer frame layout."
---

NWP transfer frames run over direct QUIC streams or the relay transport. Local IPC uses JSON-RPC.

## Layout

```text
24-byte header | payload_len bytes | 16-byte authentication tag
```

Multibyte header fields use network byte order (big endian).

| Offset | Size | Field |
| --- | --- | --- |
| 0 | 4 | Magic `NWP2` (`0x4E575032`) |
| 4 | 1 | Frame type |
| 5 | 1 | Flags |
| 6 | 2 | Stream ID |
| 8 | 8 | Sequence number |
| 16 | 4 | Payload length, excluding header and tag |
| 20 | 4 | Reserved; zero in newly constructed headers |

The parser caps payloads at 67,108,864 bytes (64 MiB). Transport limits can be lower: the relay accepts 4 MiB per WebSocket message. These are limits at different layers.

## Transfer registry

| Value | Type |
| --- | --- |
| `0x01` | `HandshakeInit` |
| `0x02` | `HandshakeResp` |
| `0x03` | `HandshakeAck` |
| `0x10` | `TransferManifest` |
| `0x11` | `ChunkRequest` |
| `0x12` | `ChunkData` |
| `0x13` | `ChunkAck` |
| `0x16` | `TransferComplete` |

Sync, Git, and tunnel frame types also exist in the registry; these products remain in development.

## Flags

| Mask | Flag |
| --- | --- |
| `0x01` | `COMPRESSED` |
| `0x02` | `URGENT` |
| `0x04` | `CONTINUATION` |
| `0x08` | `ENCRYPTED_INNER` |
| `0x10` | `PADDING` |

A flag's existence does not guarantee every path implements padding, prioritization, or fragmentation. Encrypted transfer frames use XChaCha20-Poly1305; handshake authentication binds key material to the invitation token. See the [crypto model](/protocol/crypto-model) and [source map](/spec/beta-interface).
